# Audit de wm-installer-mcp — 18 septembre 2026

État audité : dépôt au commit `00080b7` plus le working tree du jour, en cours de
modification par la session `wm-installer-mcp-cb` (install incrémental, registre
d'installations, coffre de secrets, outils `install_*` / `config_*` /
`credential_*`, `installer_check`). Les numéros de ligne cités sont ceux du
18 septembre et glisseront ; les noms de fonctions restent valables.

Le plan d'action qui en découle est dans [`plan.md`](plan.md).

## Résumé

1. **L'installer officiel ne peut plus rien installer depuis le download centre
   depuis le 28 août 2026.** Le certificat de signature de code d'IBM a expiré ce
   jour-là et `SignatureValidator` contrôle la date du jour sans honorer
   l'horodatage RFC 3161 des modules. Le job de ce matin sur `wm12` a
   échoué ainsi : 13 modules refusés, « Verification failed: validity check
   failed », puis « WISSharedBundles: Provisioning step command exited with exit
   code 5 ». Le chemin natif de ce serveur fonctionne parce qu'il vérifie le
   sha256 déclaré par le catalogue authentifié, pas la chaîne de signature du
   JAR : c'est un modèle de confiance différent, pas un contrôle équivalent.
2. **Le serveur couvre le cœur de l'installer** — catalogue, fermeture des
   dépendances, téléchargement vérifié, déballage, instance IS, profil p2,
   schémas de base — et fait deux choses que l'installer ne fait pas :
   fermer une sélection et rendre une installation incrémentale.
3. **Il ne couvre pas ce qui entoure les fichiers** : le câblage d'un package IS
   dans une instance existante, l'instance MWS, le realm UM, la désinstallation,
   la vingtaine de métadonnées que l'installer écrit et que son outillage relit,
   les switches d'entreprise (proxy, TLS client, `-scriptErrorInteract`,
   `-masterPassword`, validation d'image), et l'installation d'Update Manager
   lui-même.
4. **`fix_apply` est dangereux tel quel** sur un profil réel : il réécrit les
   deux lignes d'un bundle présent à deux versions, rétrograde silencieusement si
   on lui donne une version plus ancienne du fix, et n'avertit que pour les
   profils nommés par la recette alors qu'il en réécrit d'autres. Un fix appliqué
   nativement reste invisible pour Update Manager, qui le réappliquera.
5. **Deux fuites de secrets réelles** : la description de `image_build` invite à
   passer les identifiants dans `env`, que le wrapper de job écrit en clair dans
   `run.sh` ; et Update Manager déverse l'environnement hérité dans
   `UpdateManager/logs/debug/*.log` (mode 644), où un jeton de session figure
   déjà huit fois.
6. **Le chantier en cours répond aux huit manques remontés par la session de
   démo** (six faits, deux en cours) ; ce qui reste est ailleurs.
7. Command Central est hors périmètre (déprécié, décision utilisateur).

## 3. Retour terrain du 18 septembre

### 3.1 Deux jobs de l'installer officiel, deux échecs différents

`install-840148` (installer 12.1.0.0.123) : refusé par le serveur avant tout
téléchargement, « Your Installer Client is version 12.1.0.0.123 033026. The
server requires changes introduced in Installer Client version 12.1.0.1.153 or
later ». Couvert depuis par la signature `installer-client-outdated` de
`diag.rs` et par `installer_check`, qui refuse de démarrer `install_run` et
`image_build` avec un client plus vieux que le produit `WIR` du catalogue.

`install-869858` (installer 12.1.0.1.153, récupéré à la main) : passe le
contrôle de version, télécharge, puis échoue dans l'étape de provisioning
`WISPCFPP` :

```text
Cannot mirror products from https://sdc.webmethods.io/dataservewebM121/repository/
  Level: 1: Incomplete mirroring Build modules.
  Level: 2: Signature Verification for e2ei,11,DEP_12.1.0.0.1560,BM_Deployer-ALL-Any.zip
            failed with  Verification failed: validity check failed
  (… 13 modules …)
APP_ERROR> WISSharedBundles: Provisioning step command exited with exit code 5
```

Le certificat extrait d'un module du cache porte `notAfter = Aug 28 23:59:59
2026 GMT` (CN International Business Machines Corporation), et les modules
portent bien un jeton d'horodatage RFC 3161 dans `META-INF/SIGNER.RSA`. Le
validateur de l'installer ne l'honore pas. Conséquence : **aucune machine ne
peut installer un produit 12.1 depuis le download centre avec l'installer
officiel tant qu'IBM n'a pas re-signé les modules ou corrigé le client.** Couvert
par la signature `installer-signature-validity`, avec l'avertissement de ne pas
reculer l'horloge.

L'historique de l'installer (`install/history/history.txt`) enregistre pourtant
« products installed: 17 » pour ce run. Les `.prop`, eux, disent vrai : vérifié
aux horodatages par la session `cb`, l'installer n'a écrit que trois `.prop`,
pour les trois produits qu'il avait réellement posés, et aucun pour les treize
en échec. L'installation a ensuite été complétée par le chemin natif
incrémental (job `install-spec-879574` : 13 produits, 51 déjà présents,
1 changement de version non effectué).

### 3.3 Ce qu'une installation réelle exige, et ce que le serveur en couvre

Le runbook Trading Networks du kit de démo décrit six étapes. Le serveur en
couvre trois.

| Étape du runbook | Couverture |
|---|---|
| 1. installer IS, Flat File, TN, EDI, EDIINT, MWS, DCC | oui (`native_plan` / `native_install`) ; la dépendance cachée sur `WmFlatFile` est un cas connu du résolveur |
| 2. appliquer les fixes IS, EDIINT, EDI, MWS avec Update Manager | partiel : trouver et télécharger oui ; appliquer nativement est risqué (§5.1) et invisible pour SUM ; **installer Update Manager lui-même** reste manuel alors que l'installer sait le faire depuis le download centre |
| 3. créer les schémas **par produit** (`dbConfigurator -pr TN`, `-pr IS`, `-pr MWS`) | partiel : `database_configure` travaille par composant avec prérequis ; le mode `--product` du configurateur, que le runbook recommande, n'est pas exposé, ni les actions `drop`, `recreate`, `migrate`, `rollback`, `catalog` |
| 4. pool JDBC, alias fonctionnels, `cache=true` sur l'alias TN | non ; **et c'est dans le périmètre de l'installer** : c'est ce que `TNServerConfigPanel` et `TNServerInstallPanel` écrivent dans l'instance pendant l'installation (§4.3) |
| 5. désactiver `WmIntegrationLiveServer` et `WmIntegrationLiveGit` | non ; hors périmètre de l'installer (configuration du runtime) |
| 6. redémarrage complet et vérification | non ; idem |

Le cas Deployer de ce matin illustre l'écart le plus concret : l'archive
`BM_Deployer-ALL-Any.zip` ne contient que `IntegrationServer/packages/WmDeployer/`,
le dépôt partagé. L'installer officiel copie ensuite le package dans l'instance
choisie (`persist.prop` : `Deployer,instance.name=default`,
`package.list=WmDeployer`) ; l'install native s'arrête au dépôt partagé, et le
package a été copié dans `instances/default/packages` séparément, trois minutes
plus tard, par `is_instance.sh update`. Rien dans le serveur ne fait ce câblage.

### 4.4 Métadonnées écrites par l'installer et absentes d'une install native

Relevé sur `wm12` (installer officiel) contre le journal d'une install
native (`install/bms/*.contents`, `install/products/*.prop`, `install/jars`).

| Fichier | Qui le relit | Install native |
|---|---|---|
| `install/products/*.prop` | tout l'outillage IBM | écrit, **sans** `installDate`, `jars`, `panels`, composants — `InstallationTracker` de SUM compare `installDate` à l'horodatage des fixes |
| `install/bms/*.contents` | désinstalleur, `-queryInstall` | écrit, sans les modes |
| `sagProducts.xml`, `sagMetadata.xml`, `p2.index`, `install/features/*.prop.iu.jar` | dépôt p2 des produits : Platform Manager, SUM | absents |
| `install/history/history.txt`, `audit.log` | opérateur, support | absents |
| `install/etc/installconfig.prop` (JVM, versions client et serveur), `persist.prop` (réponses des panels : ports, instances, `db.*`) | installer aux exécutions suivantes, panels | absents |
| `install/instance_registry.xml` | instance manager, SUM (`osgiShutdown profile:…`) | écrit par `is_instance.sh` uniquement |
| `install/profiles/<p>.data` | `P2ProfileRecreatorPhase` de SUM (reprovisioning après fix) | absent |
| `bin/uninstall`, `install/etc/uninstall.template` | désinstallation | absents |
| `~/.sagconf.xml` (registre des installations, `SAGEnv`) | `-queryInstall`, `-uninstallEveryInstall` | absent ; le registre `registry.rs` est parallèle |
| `install/fix/{profile,backup,readme,logs}` | SUM (§4.7) | absents |

Une install native est donc complète pour le runtime et pour ce serveur, mais
partiellement illisible pour le désinstalleur et pour Update Manager. Le
serveur ne le dit nulle part.

### 4.5 Désinstallation

Officiel : `DistManUninstallMain` via `bin/uninstall`, scripts
`-readUninstallScript` (clé `InstallLocProducts`), `-uninstallEveryInstall`,
mode revert (`install/revert/{products,bms}`) ; la suppression suit
`install/bms/*.contents`, arrête les instances, retire profils et services.
MCP : **rien**. Une install native n'a ni `bin/uninstall` ni les jars que le
désinstalleur chargerait ; la seule voie serait native, à partir des `.contents`
que `native_install` écrit déjà.

### 4.8 Hors périmètre de l'installer

Deux familles de besoins sortent du périmètre de l'installer et donc de cet
audit, mais reviennent dans chaque installation réelle : la configuration du
runtime après installation (packages à désactiver, démarrage, arrêt et
vérification, étapes 5 et 6 du runbook ; le câblage JDBC de TN, lui, est un
panel de l'installer) et la migration entre releases, que la documentation IBM
décrit comme une nouvelle installation côte à côte suivie des utilitaires de
migration par produit et du configurateur de base, jamais comme une fonction de
l'installer. Ce sont des candidats à un troisième serveur, pas des évolutions
de celui-ci.

Une remarque sur les sources : IBM ne documente ni les clés du script
d'installation ni celles du script d'Update Manager (les notes techniques qui
en parlent sont derrière authentification), ni les codes de sortie. Les
lectures décompilées de `docs/installer-protocol.md` et `docs/sum-protocol.md`
sont, à ce jour, la seule référence écrite.

### 5.2 Importants

Jobs et exécution :

- `--watch` ne rend jamais la main sur un job natif échoué : `progress.finish`
  n'est appelé que sur succès (`native.rs` l. 1186), le chemin d'erreur sort par
  `exit(1)` sans finaliser `progress.json`, et `watch()` ne retourne que sur
  `finished.is_some()` (`main.rs` l. 80).
- le spec de job s'appelle `install-spec-<pid du serveur>.json` : deux
  `native_install` rapprochés depuis le même serveur écrasent le même fichier
  avant lecture ; le spec n'est jamais supprimé (`native.rs` l. 648).
- aucun pid enregistré, aucune détection de job mort, aucune annulation, aucun
  nettoyage des jobs ni du cache d'artefacts ; le `Child` est droppé sans `wait`
  (zombie par job).
- `run_console` : au timeout, `child.kill()` tue `UpdateManagerCMD.sh` et pas le
  JVM fils, qui survit avec ses verrous ; l'appel suivant refuse (« stale
  lock ») et `sum_locks remove=true` supprimerait les verrous d'un SUM vivant.
  Il faut tuer le groupe de processus. L'heuristique « 8 s de silence ⇒ Entrée »
  peut alimenter le prompt suivant pendant un self-update muet ; le dernier
  fragment de sortie avant la fin peut être perdu.
- `fixes_installed` est synchrone jusqu'à 600 s dans une boucle mono-thread :
  tout le serveur est bloqué.
- les jobs de l'installer officiel sont lancés sans `-scriptErrorInteract no`.

Réseau et cache :

- `timeout_global(300 s)` s'applique à la requête entière, corps compris : un
  artefact de 300 Mo sur un lien lent échoue ; aucun retry ; le grant du
  protocole G est renouvelé sur horloge locale (15 min) sans réaction à un 401.
- le corps du product tree est écrit en cache **avant** validation
  (`native.rs` `tree_for`) : une page HTML servie en 200 est mise en cache et
  parse à 0 produit jusqu'à `refresh: true` ; aucun âge ni TTL exposé.
- vérification sha256 en mémoire puis `fs::write` non atomique dans le cache,
  puis relecture pour déballer : deux jobs partageant le cache peuvent se
  tronquer mutuellement.

Fixes (en plus de §5.1) :

- `osgiShutdown(profile:SPM|CCE)` : le séparateur `|` n'est pas géré.
- `Require-Fix`, `Install-After`, `Fix-Version` ne sont pas lus ;
  `Require-SUM-Build` est lu mais jamais comparé à `bin/config.properties`.
- rollback : un seul `bundles.info.before-fix`, écrasé à chaque fix, copie
  dont l'erreur est ignorée ; aucun backup des fichiers extraits ni supprimés ;
  pas de transaction (échec en phase 5, phase 4 appliquée).
- aucune vérification de signature ni de sha256 dans `fix_apply` : une archive
  arbitraire peut `delete(file:profiles)`.
- `selectedFixes` vide ne signifie pas « tous les applicables » : SUM répond
  « Empty selectedFixes found in the silent script file. Performing only
  self-update » (vérifié dans `wm12sum/bin/result.json`) ; `sum.rs` et la
  description de l'outil disent le contraire ; `fix_script_generate` ne produit
  jamais de batch malgré sa description.
- `stale_locks` ignore `<installDir>/SumWorksOnThisDir.lock` et ne teste pas la
  vivacité du processus.

Provisioning :

- `java_home()` du chemin natif d'instance prend le **dernier** sous-répertoire
  de `jvm/` contenant `bin/java` par ordre lexicographique : sur wm12 c'est
  `jvm/jvm0001.bck`, la sauvegarde d'une mise à jour de JVM, qui finit dans
  `setenv.sh` et `wrapper.conf`. Les trois autres chemins codent `jvm/jvm` en
  dur ; la « découverte » est la fausse.
- aucune canonicalisation de `wm_home` : `profile::capture` tokenise par
  `wm_home.display()`, donc un chemin relatif, un slash final ou un lien
  symbolique produit une capture non rejouable ou qui garde les chemins de la
  machine source ; le registre p2 porté tel quel (`*.profile.gz`, binaire)
  contient 196 occurrences de `wm12` et n'est pas tokenisé.
- traversée par le nom : `validate_name` ne s'applique qu'au chemin natif ;
  `-Dinstance.name=../x` sur le chemin Ant, `profile_replay` et
  `profile_provision` joignent le nom sans contrôle.
- idempotence : une instance à moitié créée est réécrasée en silence par le
  script (`validateInstanceExist` n'échoue que si `bin/` et `configuration/`
  sont non vides) ; `profile_replay` écrase avec un simple avertissement ;
  `database_configure` renvoie `Err` au n-ième composant et **perd** la liste
  de ceux déjà configurés.
- Ant, director et configurateur sont lancés en synchrone sans timeout dans la
  boucle mono-thread : un blocage bloque le serveur ; le succès est détecté par
  chaîne (`BUILD SUCCESSFUL`, `status         : complete` avec espacement
  exact).
- `profile_capture` écrit immédiatement, sans `apply`, alors que les
  instructions du serveur promettent un dry run pour tout ce qui change quelque
  chose ; le dry run natif d'`instance_create` ne renvoie que `{"native":true}`.
- le chemin natif d'instance accepte `license_file` et `db_*` puis les ignore
  sans avertissement ; `instance_create` ne vérifie pas la présence de
  `install/jars/DistMan.jar` malgré sa description.

Scripts et validation :

- `script.rs` : aucun échappement `.properties` ; `LicenseAgree` non contrôlé ;
  `placeholders()` ne scanne ni `install_dir`, ni `extra`, ni `products`.
- `panels=` vide dans le tree produit `[""]` : le produit est compté comme
  déclarant des panels.
- `catalog::load` échoue sur un seul `.prop` illisible alors que la doc promet
  de le sauter.

Portabilité :

- des binaires Windows sont publiés (`release.yml`) mais `runner::spawn` écrit
  un wrapper `#!/bin/sh` lancé par `sh` / `setsid`, `run_console` est
  `cfg(unix)` sans stub, `config::home()` lit `HOME` : aucun job ne démarre
  sous Windows, et le build de `wm-sum-mcp` y est probablement cassé. Le README
  dit « the Update Manager path is Unix-only », c'est tout le chemin job qui
  l'est.

Textes trompeurs :

- `diag.rs` l. 160 conseille `installer_fetch`, qui n'existe pas ;
- `fixes_download` : « Applying a fix still needs Update Manager » contredit
  `fix_apply` ; `fix_inspect` dit « need a p2 director » pour des actions
  fichier ; `fixes_installed` dit `-viewInstalledFixes` alors qu'il génère un
  `-readScript` ; `docs/download-protocol.md` « What is not reimplemented —
  Applying a fix » est antérieur à `fix.rs`.

### 5.3 Mineurs (sélection)

`BadPattern` et la dépendance `regex` sont morts ; `Exec(String)` est le
fourre-tout de tout le réseau, des digests et des exécutions ; `flag()` ignore
silencieusement une valeur non booléenne ; `platform` n'est jamais validé ;
`installerVersion=12.1.0.0.123` et `UpdateManagerVersion=12.0.0.0008` sont codés
en dur ; artefacts et modules chargés intégralement en mémoire ; `___symlinks`
cassé sur un lien avec espace ; parseurs XML de `fixes.rs` faux sur un élément
auto-fermé (échec sha256 à tort, jamais l'inverse) ; `tail()`, `install_dir()`,
le filtre de recherche et le bloc login → releases → sandbox sont dupliqués ;
désignation de l'installation incohérente (`wm_home` + `install` d'un côté,
`install_dir` de l'autre, `sum_home` à part) ; le serveur SUM ignore
`config::Defaults`.

## 6. Tests, CI, documentation

- 148 tests unitaires, bonne couverture de `deps.rs` (10) et `diag.rs` (7) ;
  **rien** sur `tools.rs`, `native.rs`, `main.rs`, `mcp-rt`, `wm-sum-mcp`.
- Chemins critiques sans test : `unpack` sur une vraie archive, `fetch` (cache,
  digest divergent), `fix::apply` de bout en bout, `bundles.info` avec un bundle
  à deux versions, `run_console`, `Report::read`, `read_result` sur un vrai
  `result.json`, tout client HTTP (aucun faux serveur).
- CI : fmt, clippy `-D warnings`, test, `cargo audit` ; release sur cinq cibles
  dont deux Windows non fonctionnelles.
- Docs : trois affirmations fausses relevées (§4.7), un README qui ne dit pas
  qu'une install native est partiellement illisible pour l'outillage IBM
  (§4.4), `main.rs` qui ne documente qu'un tiers des variables d'environnement.
  Sur le provisioning, les docs décrivent trois états successifs sans marquer
  les anciens comme historiques : `install-panels.md` dit « reimplemented » puis
  « superseded », puis « Eclipse p2 profiles — now native » et « Database
  schemas — now native », tous deux faux aujourd'hui ; le module `database.rs`
  décrit encore l'exécution SQL native qui a été retirée (`split_statements`
  n'est plus appelé que par ses tests) ; `instance.rs` présente le chemin natif
  comme principal alors que le chemin Ant est le défaut ; le README attribue
  `PortalStartConfiguratorSerenity` à Trading Networks.

## 7. Les douze écarts qui comptent

Par ordre d'importance pour quelqu'un qui installe, corrige et retire
webMethods sans le wizard, aujourd'hui, sur ce genre de plateforme.

1. `fix_apply` doit refuser de rétrograder, indexer par (nom, version) et
   avertir pour tout profil qu'il touche (B1, B2, B3) avant toute nouvelle
   utilisation avec `apply=true`.
2. Deux fuites de secrets à fermer (B4, B5).
3. Un fix natif doit être connu : lire le profil `self` pour `fixes_installed`
   et pour `installedFixes`, refuser un fix déjà posé, puis enregistrer ce qui
   est posé (registre, cache, backup, readme) ou fabriquer une image que SUM
   installe et enregistre lui-même.
4. Câbler un package IS installé nativement dans les instances existantes
   (`is_instance.sh update`), poser la licence que `license_file` prétend
   poser, écrire le pool et l'alias JDBC de Trading Networks comme le panel le
   fait, et plus généralement mettre à jour et supprimer une instance.
5. Installer Update Manager lui-même depuis le download centre, comme
   l'installer le fait.
6. Rendre une install native lisible par l'outillage IBM : `.prop` complets,
   `.contents` avec modes, `installconfig.prop`, `history`, `~/.sagconf.xml`,
   `install/profiles/<p>.data`, `bin/uninstall`.
7. Désinstaller (natif depuis `.contents` ; officiel via `bin/uninstall` et
   `InstallLocProducts`).
8. Robustesse des jobs : `--watch`, spec par job, pid et annulation, groupe de
   processus du pty, `-scriptErrorInteract no`, espace disque, verrou par home,
   cache du tree validé et daté.
9. Ordonner et enchaîner des fixes (`Require-Fix`, `Install-After`), et gérer
   les actions de recette au moins pour les fixes IS et MWS courants.
10. Les six actions manquantes de `dbConfigurator` et son mode par produit ;
    l'instance MWS et le realm UM.
11. Parité d'entreprise : proxy, TLS client, `-masterPassword`, validation
    d'image, innovation releases, `extra_args`.
12. Un socle de tests d'intégration (faux download centre, archives forgées,
    couche MCP) et une position honnête sur Windows.

Le découpage, les priorités et l'attribution sont dans [`plan.md`](plan.md).
